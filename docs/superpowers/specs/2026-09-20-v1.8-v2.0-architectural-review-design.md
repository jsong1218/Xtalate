# Design — v1.8 + v2.0 Architectural Review

**Date:** 2026-09-20
**Branch:** `v1.8-v2.0-architectural-review` (off `m76-refreeze-release`, which carries the 2.0.0 version flip)
**Scope:** the combined post-release architectural review of **v1.8 "Analysis Plugin Surface" (M68–M71)** and **v2.0 "schema 2.0.0 / variable-N / H5MD" (M72–M76)**, folded **into** the `2.0.0` release before the maintainer tags it (standing rule: each version's architectural review folds into that version before tagging — the v1.2/v1.3 and v1.6/v1.7 precedents).

**Decisions locked with the user:**
1. **Fold into 2.0.0** — no extra version bump; fixes land under the existing `[2.0.0]` CHANGELOG section as a "Fixed" block. The maintainer tags `v2.0.0` once, nightly-green-gated (D52).
2. **Add Dependabot** — grouped, scheduled, review-gated (never auto-merge); runtime version *ranges* in `pyproject.toml` stay maintainer-controlled. Update the scorecard.yml exception note.
3. **Fuzzer = in-repo Atheris + ClusterFuzzLite** — a `.clusterfuzzlite/` config + an Atheris harness over the parser surface, CI-run as a **short, advisory (non-blocking)** batch on PRs, with the long batch under nightly. No external OSS-Fuzz onboarding required (that would need a maintainer submission to `google/oss-fuzz`).

This review is unusual: it is **not** greenfield design. The "design" is (a) the confirmed defect inventory, (b) the fix approach per defect, and (c) the slice decomposition. The review was performed by six parallel read-only Sonnet agents; every code anchor below was independently re-confirmed against the tree.

## 1. Confirmed defect inventory

### A. Variable-N per-atom correctness (v2.0 M72/M73) — **P1 violations, the highest priority**

Schema 2.0.0 relocated `custom_per_atom` from the object header onto each `Frame`, and M73 **retired the constant-N reader refusals** (commit `98cb413`) that used to guarantee a uniform per-atom key set and atom count across all frames. Several code paths still assume "frame 0 is representative of every frame" — an assumption M73 made false. The result is silent scientific data loss and, worse, silent *wrong-value substitution*, on exactly the variable-N workflows v2.0 exists to support.

- **V1 [HIGH] — `convert_stream` silently drops a per-atom column that first appears after frame 0.**
  `src/xtalate/conversion/engine.py`: the `custom_per_atom` write-plan refinement runs once, latched by `per_atom_refined` after **frame 0** (`_planned_frames`, ~1013–1030), and every later frame is filtered against that frozen plan (`_kept_custom` ~1993–2001, applied in `_filter_frame` ~2038). The justifying comment (~989–999) explicitly cites "the reader refusals still gate divergence" — refusals that no longer exist post-M73. A later frame introducing a new per-atom key has that key silently discarded, **no warning emitted**. Reproduced on extXYZ→extXYZ (the engine's own documented streaming pass-through). Breaks the M73 streamed/materialized identity theorem (the materialized `convert()` path re-derives the plan from full presence and does not have this blind spot).

- **V2 [HIGH] — extXYZ *streaming* parser substitutes frame 0's per-atom values into later same-N frames.**
  `src/xtalate/parsers/extxyz.py:443–447`: `if len(atoms) == len(first_atoms): frame_per_atom = coerced_per_atom` reuses **frame 0's** already-coerced column values for any later frame that merely shares its atom count, instead of recomputing that frame's own columns (the `else` arm at 447 already does the right thing). Reproduced: a 4-frame file N=[5,5,3,5] with a distinct `foo` column per frame yields frame 0's values for frames 1 and 3 in the streaming parse, diverging from the (correct) materialized parse. Emits `EXTXYZ_PER_FRAME_COLUMN_NOT_REPRESENTABLE` whose justification ("`custom_per_atom` is object-level, Part 2 §3.10", `extxyz.py:546,827`) is itself stale post-M72. This is *wrong data presented as real* — worse than a drop — and a direct violation of the identity theorem.

- **V3 [HIGH, to confirm via TDD] — same frame-0-substitution idiom in `lammps_dump.py` and `ase_traj.py`.**
  `src/xtalate/parsers/lammps_dump.py:~930–1010` (see `_build_frame` docstring ~958–962) and `src/xtalate/parsers/ase_traj.py:~166–201` carry the identical `if len(atoms) == n_atoms: frame_per_atom = <frame-0 values>` structure. `ase_traj.parse()` is `materialize(parse_stream(...))` (single path, so no streamed/materialized *divergence*), but the wrong-value substitution still occurs whenever two frames share an atom count and differ in per-atom values. The agent could not force ASE's `.traj` writer to persist custom columns in a throwaway harness; the fix must ship with a test that does (or an xfail with a recorded reason if ASE genuinely cannot round-trip a per-atom column).

- **V4 [MED-HIGH] — presence is derived from frame 0 only; a later-frame-only key is invisible, not even "absent."**
  `src/xtalate/schema/presence.py`: materialized `compute_field_presence` iterates `obj.frames[0].custom_per_atom` (~174); the streaming `PresenceAccumulator` seeds `_custom_per_atom_keys` once (~265–268) and consumes it at ~296. Both agree with each other (so this does **not** break the identity theorem) but both are wrong under variable-N: a key introduced in frame 2 of a 3-frame trajectory produces **no `PathPresence` entry at all**. Undercuts P1 (every loss is reported) and P3 (absence is information), and makes V1's dropped column doubly invisible — the report never claimed to preserve it.

- **V5 [LOW / latent] — `validation/streaming.py` folding never applies M73's `_perm_for(perm, n)` length guard.**
  `_fold_species` (~175), `_fold_positions` (~181), `_fold_numeric` (~234) index/permute via `self._perm` with no per-frame length check, unlike `validation/engine.py`'s batch `_perm_for(perm, n)` (identity fallback on size mismatch). Masked today because `validate_stream()` hardcodes `perm=None` (~614–617), justified by the streaming-eligibility gate admitting only order-preserving exporters. A defensive `_perm_for`-equivalent guard removes the latent `IndexError`/miscompare a future reordering variable-N streaming exporter would trip.

**Reviewed and sound (no action):** `schema/migrations.py::_relocate_custom_per_atom` (1.0.0→2.0.0); the `capabilities/` `supports_variable_atom_count` axis (safe `False` default) and `conversion/preflight.py` refusal-to-`frame_selection` for constant-N targets (no pad/truncate path); the batch-path `_perm_for` guard; the refusal-retirement sites themselves.

### B. H5MD (v2.0 M74) — security hardening + P1 honesty

- **H1 [CRITICAL] — unbounded per-frame array size OOM, defeating `max_frames`.**
  `src/xtalate/parsers/h5md.py`: `_build_frame` (~480–514) and `_Element.at()` (~165–168) allocate a frame's `position`/`velocity`/`force`/`mass`/`charge` row with no bound on the particle dimension. An HDF5 VLEN row can independently declare an arbitrary length; a 3-frame file where one row is ~2×10⁹ float64 → multi-GB alloc. Because `enforce_max_frames` (`src/xtalate/sdk/streaming.py:234–268`) counts frames by iterating them, the OOM fires **during the count-only precheck**. `max_frames` bounds count, never per-frame size.

- **H2 [CRITICAL] — eager full-dataset load for any "fixed-in-time" element, no shape check, before frame counting.**
  `h5md.py:159–163`: the `else` branch does `self._fixed = np.asarray(node)` unconditionally for `species`/`mass`/`charge`/bare `velocity`/`force`/`box/edges`, and again in `_resolve_observables` (~535–561). A crafted `particles/all/species` with declared shape `(2_000_000_000,)` (cheap via chunked/sparse HDF5) triggers ~16 GB alloc the moment the file is opened — before `n_steps` is computed, before `_edges_to_lattice`'s shape check (~187–199) runs.

- **H3 [HIGH] — no HDF5 external-link mitigation.**
  Group traversals (`f.get(...)` at ~588,546,567; `group.get(name)` in `_resolve` ~172) dereference objects with no `getlink=True` check for `h5py.ExternalLink`, and `h5py.File(stream, "r")` (~322) sets no property list disabling external-link resolution. An external link stores an OS path that h5py opens directly on dereference, independent of the fileobj driver — in the upload-accepting service this is a file-existence probe / arbitrary-HDF5-read surface. Mitigation: refuse any external/soft-link-to-external node (there is no legitimate H5MD use for one here).

- **H4 [MED] — cheap huge-frame-count CPU DoS.** `_frame_count` (~438–471) trusts `position.length`/`step_len` as the loop bound with no ceiling; a sparse/chunked `step`/`value` shape `(10**9,)` occupies a few KB but drives ~10⁹ iterations. CLI/library callers pass no `max_frames` and are unprotected.

- **H5 [HIGH] — `frame.time` never read → exporter silently fabricates it on round-trip.**
  `_build_frame` (~474–533) never passes `time=` to `Frame(...)`, so `frame.time` is always `None` after an H5MD parse. The exporter's `_frame_time` (`src/xtalate/exporters/h5md.py:297–300`) then writes `float(index)` for every frame — synthetic `[0,1,2,…]` replacing real non-uniform times, **no Assumption/warning**. `frame.time` is a capability leaf (`schema/paths.py:46`) but is declared by neither `capabilities()` (parser ~603–631, exporter ~263–294), so the Matrix does not even flag the loss.

- **H6 [HIGH] — mass/charge length mismatch silently laundered to `None`.**
  `h5md.py:492–495,511–514`: `masses = arr if arr.shape[0] == n else None` (and charge) — a *present-but-inconsistent* array is dropped indistinguishably from an honestly-absent one, no `ParseIssue`. P1 violation, and realistic under the very variable-N files M74 targets.

- **H7 [MED] — torn-tail recovery only inspects `position`.** `_frame_count` derives `n_steps` from `position` alone; if `velocity`/`force`/`mass`/`charge`/`box`/`observables` is torn while `position` is intact, `.at(index)` (~500–514, `_BoxReader.at` ~209–210, observables ~426–429) raises a raw h5py exception instead of the promised `H5MD_TRUNCATED` recovery (only the `Frame(...)` construction is wrapped, ~520–533).

**Reviewed and sound:** unit-conversion factors (`_LENGTH`/`_VELOCITY`/`_FORCE`/`_ENERGY`/`_MASS`/`_CHARGE`, ~83–108); the absent/unrecognized/recognized-unit laundering distinction; multi-particle-group and missing-required-group refusals; the benign-case streaming bound; the position/species variable-N mapping and its `H5MD_INCONSISTENT_FRAME` shape check.

### C. v1.8 Analysis Plugin Surface (M68–M71)

- **A8-1 [HIGH] — analyze `results` is rebuilt by prefix-rescanning `custom_global`, not from the plugin's actual returned entries.**
  `backend/jobs/runner.py:392–403` and `src/xtalate/cli/main.py:563–570` both do `results = {k:v for k,v in annotated.user_metadata.custom_global.items() if k.startswith(f"{plugin.name}:")}`. But `run_analysis` (`src/xtalate/sdk/analysis.py:64–83`) **merges** the plugin's `entries` into the pre-existing `custom_global` (`{**existing, **entries}`). A plugin whose `name` collides with a parser carry-through namespace (`lammps_data`, `qe`, `poscar`, `xdatcar`, `contcar`, `ase_db`, …) will sweep pre-existing source-carried data into "results the plugin wrote," contradicting the written contract in `backend/models.py`'s `AnalysisReport` docstring and `DEVELOPER_GUIDE.md` §8.6. `run_analysis` already computes the exact `entries` and records `keys=sorted(entries)` in the appended `ConversionRecord`.
  **Structural root cause:** `Registry.register_analysis_plugin` (`src/xtalate/capabilities/registry.py:146–160`) guards only against duplicate analysis-plugin names — not against a name colliding with a parser/exporter `format_id` or a carry-through prefix.

- **A8-2 [MED] — the composition/density reference plugin's `frames[0]`-is-representative design is stale under variable-N.**
  `plugins/xtalate-analysis-composition/src/xtalate_analysis_composition/analysis.py::_density` / `analyze` compute formula/element-counts/density from `canonical.frames[0]` only ("constant-N … a single representative density", ~82–85) — invalidated by M72/M73. `MIGRATION.md:109` ("Analysis plugins need no change from this relocation") is mechanically true but silent on the science.

- **A8-6 [LOW] — `AnalysisPlugin.name` has no runtime format/uniqueness validation** (`sdk/plugins.py:153–155` is a comment). Empty/uppercase/`:`-containing names register and behave surprisingly in the prefix logic.

**Reviewed and clean:** SDK containment + import-linter contract; plugin-exception → clean job `status:"error"` (no 500 leak); frontend Analysis tab (no `dangerouslySetInnerHTML`, `null`→"not computed", honest error/cancelled states, real e2e); `GET /v1/plugins`; `POST /v1/analyze` submit-time `422 UNKNOWN_PLUGIN`, guards, provenance.

### D. Nightly failure — issue #112

`benchmarks/harness.py:710–736` (`_bench_parse_asedb_1k_rows`) still asserts the pre-M73 `ASEDB_MULTIPLE_ROWS` refusal; M73 (`d2567f7`) made a multi-row `.db` read through as one variable-N object, so `parser.parse()` now succeeds and the benchmark hits its `else: raise AssertionError(...)` canary. Not a real bug — a stale test. Fix: assert the success path (`len(canonical.frames) == n_rows`, trajectory set) and invert the canary (fail loudly if `ParseError` *is* raised). Sweep `tests/` for other stale `ASEDB_MULTIPLE_ROWS`-as-`parse()`-outcome references. This unblocks nightly-green, which gates the D52 publish.

## 2. The fuzzer (S7) — approach

- **Target:** `ParserPlugin.parse(stream: BinaryIO, *, filename)` (`src/xtalate/sdk/plugins.py:42`), bytes-in, iterating `builtin_parsers()` (20 parsers). Contract asserted: the call returns a `ParseResult` or raises `ParseError` — **any other exception (or a hang/OOM) is a fuzz failure**. This mirrors `tests/fuzz/test_parser_fuzz.py::_assert_graceful` (304–318).
- **Harness:** one Atheris entry point that consumes a leading selector byte to pick a format, then feeds the rest to that parser (plus a DiscoveryEngine end-to-end harness variant, `discover(data: bytes)`, exercising the sniffer). Wrapped so `ParseError` is caught and anything else propagates as a crash.
- **Corpus:** seed from the existing `_TAILORED` per-format dict + `_GENERIC` cases in `tests/fuzz/test_parser_fuzz.py`, plus a sampling of the golden fixtures. Store under `.clusterfuzzlite/` seeds or `tests/fuzz/corpus/`.
- **ClusterFuzzLite:** `.clusterfuzzlite/{Dockerfile,build.sh,project.yaml}` building the Atheris harnesses; a `.github/workflows/cflite_pr.yml` running a short (e.g. 120 s) batch on PRs **advisory (non-blocking)** and a longer batch on the nightly/scheduled trigger. Add `atheris` as a `fuzz` optional-dependency (kept out of the core/runtime set; it is a CPython-version-sensitive build, so pin conservatively and document the constraint).
- **Feeds Scorecard Fuzzing** via ClusterFuzzLite detection — no OSS-Fuzz onboarding needed. H5MD fuzzing depends on `h5py` reading a `BytesIO`; include it but expect most H5MD hardening to be covered by the adversarial unit tests in S4 (a fuzzer rarely synthesizes a valid-enough HDF5 superblock).

- No refactor beyond what each fix requires (e.g. S6 may thread `entries` out of `run_analysis`, but does not restructure the analysis SDK).
- No OSS-Fuzz onboarding (maintainer submission); ClusterFuzzLite only.
- No auto-merge for Dependabot; runtime dependency *ranges* stay as-is.
- `docs/private/*` stays gitignored; no test reads it; no user-facing text cites it.
